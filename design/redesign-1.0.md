## 0. 前提と結論

### 0.1 確定済みの3本柱（ユーザー承認済み、変更不可）

1. **ロット実体シミュレーション**：集計（WPH合算）から、FOUP単位のロットが投入→キュー→処理→搬送→次工程と流れる離散シミュレーションへ。ボトルネック・滞留は式ではなく現象として起きる。歩留まり・欠陥・検査・学習はロット/装置に紐づく。
2. **自由レイアウト**：グリッド上に装置を配置・回転・移動・売却。搬送レールはプレイヤーが引く。ストッカー・出荷口も自由。床は区画購入で拡張。リエントラント（同一工程を何度も通る）を経路で表現できる。
3. **絵**：3/4俯瞰セミフォトリアルのレンダリング調スプライト。可動部をレイヤー分離してアニメーション。CMP装置サンプル（プラテン回転＋ロボットアーム＋状態ランプ）が質感基準。

### 0.3 設計の結論（先出し）

- **シミュレーション方式**：ゲーム内1分固定ステップ（実0.1秒）の離散シミュレーション。tick ごとに `floor(dt×10)` ステップ実行し端数を繰り越す。イベント駆動は 1.0 では採らない（ブロッキング搬送の意味論が固定ステップの方が単純で、オンライン/オフラインの同一性を保証しやすい）。
- **処理時間**：1ロット1パス = `25 ÷ (公称WPH × Lv倍率 × 研究倍率) ÷ 稼働率` ゲーム時間。これで定常スループットが現行の集計モデルと一致する（§1.3）。
- **搬送**：レールは「行き先を知っている」AMHS型（分岐は目的地で振り分け）。ストッカーをハブとして、全装置がストッカーと双方向に繋がっていれば任意のリエントラント経路が成立する。直結レールは近道として機能する。
- **オフライン**：ハイブリッド。上限内の時間を本シミュレーションで前進（予算 12万ステップ ≈ 実0.3秒）、予算超過分は直近の実測スループットで外挿。両者の差が目標精度（±3%）に収まることを HeadlessCheck で保証する。
- **回転**：論理4方向、絵は2方向（正面・側面）レンダリング＋左右反転で4方向をまかなう。
- **セーブ**：schemaVersion 4。資金・研究・ノード解放・図鑑・マイルストーン・統計・補助金・学習は保持。フロアはテンプレートで再構成し、収まらない装置は倉庫へ。

### 1.2 時間とステップ

- **シミュレーション刻み** Δ = ゲーム内1分（実0.1秒）。`Engine.tick(dtRealSeconds:)` は `dt × 10` 分を加算し、整数分だけ `SimCore.step()` を回し、端数を `fab.sim.pendingMinutes` に繰り越す。
- **1ステップの処理順**（決定的。乱数は使わない）
  1. 装置：処理中ポートの `remaining -= 1`。0 になったら `.done`。
  2. 装置：空ポートがあり `.waiting` ロットがあれば先頭を `.processing` に（処理は1台1ロット同時、バッチ無し。§8-12）。
  3. 出発：`.done` のロットについて次ステップの行き先を決定（§1.5）。経路先頭セルが空なら出発、ポートを解放。
  4. 搬送：レール上のロットを進める（`progress += 1/3`。1セル = 3ゲーム分）。次セルが埋まっていれば停止（ブロッキング）。合流は待ち時間が長い方を優先。
  5. 到着：装置ポートが空けば入線、満杯ならレール末端で待つ（上流がブロックされる）。ストッカー到着は容量内なら収容。
  6. 完了：最終ステップ（PKG）の `.done` は出荷口へ搬送され、到着時に販売（§4）。
  7. 投入：Entry から最初のステップの行き先が確保でき、全体 WIP < 200 なら新ロットを1個投入（プル方式。学習枚数 W に 25 を加算）。
  8. 統計：稼働率 EMA、滞留、スループット EMA を更新。
- オンライン tick（0.25秒）は 2〜3 ステップ。オフラインは §1.8。
- 市況・研究・補助金・異常抽選・マイルストーン評価は従来どおり tick 単位（ステップ単位ではない）。

### 1.3 処理時間の導出（WPH 定数からの変換）

```
T_pass(モデル m, Lv) [ゲーム分] = 25 ÷ (nominalWPH_m × (1 + 0.1(Lv−1)) × 研究throughput倍率) × 60 ÷ min(0.85 + 研究uptime加算, 0.99)
```

- 稼働率は 1.0 では**決定的な時間倍率**として扱う（段取り・ロード/アンロード込みの実効時間）。確率的なチョコ停は §8-2。
- 定常状態の工程スループット = Σ台 (25 ÷ T_pass) ÷ パス数 [枚/時] = 現行の `processWPH` と一致する。ラインの定常スループットはその最小値（＝現行 lineWPH）に搬送制約が加わる形になる。
- 改良（Lv）・研究の効果は T_pass の短縮としてそのまま効く。

### 1.4 ルート（リエントラントの表現）

ルートは「工程ステップの列」。既存の `NodeSpec.passes`（と露光オーバーライド）から**決定的に生成**し、ステップ総数はパス数の合計と一致させる（スループット等価性の根拠）。

生成規則（`RouteBuilder.route(node:, lithoClass:)`）：
- 層数 L = 露光パス数。層 i = 1…L について `[成膜, 露光, エッチ]`。
- 注入パスは層 1…n_implant の直後に付ける（FEOL）。
- 成膜・エッチの余剰（dep−L, etch−L）は後ろの層から `[成膜, エッチ]` の追加ペアとして付ける（デュアルダマシン相当）。
- CMP は最後の n_cmp 層の末尾（BEOL 金属層）。
- 検査は層 round(k×L/n_insp)（k=1…n_insp）の末尾。
- 最後に PKG。
- 全ノードで dep≥L、etch≥L、implant/cmp/insp ≤ L が成り立つことを確認済み（7nm EUV は L=35 で余剰 45）。

28nm（L=15）の例：層1〜8 `成膜→露光→エッチ→注入`、層9〜10 `成膜→露光→エッチ`、層11〜15 `成膜→露光→エッチ→成膜→エッチ→CMP`、検査は層5・10・15 の末尾、最後に PKG。計 72 ステップ。

露光クラス混在の扱いは現行ルール A（稼働中の最上位クラスでパス数を決め、どの露光機でも処理できる）を**投入時に固定**して踏襲する。1.1 で「クリティカル層は EUV のみ」に分ける案を §8-8 に残す。

### 1.5 経路選択（ルーティング）

- 装置 A でステップ完了 → 次ステップの工程 p の候補装置 B（ロットのノードに対応し、A の出力ポートからレールグラフで到達可能）を列挙。ストッカーは「任意の入口から入り、任意の出口へ出られるノード」で、取り扱い時間 10 ゲーム分を加算。
- スコア = 搬送時間（最短経路セル数 × 3分 + ストッカー経由なら +10分）+ 予想待ち（B のポートにいる各ロットの残り時間の合計 + 処理中の残り）。最小を選ぶ。同点は ID 順（決定的）。
- 経路は出発時に確定。レール編集で経路が切れた場合、そのロットは「手運び」でストッカーへ移される（§2.4）。
- 候補が 0 なら `.done` のままポートに留まり、装置に「行き先なし」バッジ。全ポートが埋まると装置は停止（＝ライン寸断が可視化される）。
- 投入時の最初のステップ（成膜）も同じ規則。候補が無ければ投入停止。

### 1.6 搬送容量と速度

| 項目 | 値 | 根拠 |

### 1.7 ボトルネック・デッドロック・寸断・空転の検出と提示

| 現象 | 検出 | 提示 |
|---|---|---|
| ボトルネック（実測） | `busyEMA` 最大かつ待ちロット数が最大の装置／工程 | 現行どおり赤脈動。カードに「待ち N FOUP」 |
| ボトルネック（理論） | 静的容量解析（現行 `derived` 式を配置・接続済み装置で計算） | パネルに「理論上限 X WPH」。実測との差が搬送・配置の損失 |
| 滞留 | レール上で停止中のロット数、ストッカー在庫 | FOUP の上に砂時計、レールが黄色く点灯 |
| ライン寸断 | ルートの連続ペア (p_i→p_{i+1}) のうち接続済み装置ペアが無いもの | レイアウトパネルのチェックリスト「エッチ→成膜（戻り）✗ レールが足りません」 |
| 未接続装置（空転） | 入力がどこからも到達不能、または出力がどこにも到達不能 | 装置をグレー表示＋「未接続（入口／出口）」。容量解析から除外 |
| デッドロック | WIP>0 かつ 60 ゲーム分連続で「出発・到着・処理完了」が 0 回 | 赤バナー「ラインが詰まっています」。詰まりの輪（ブロックされたセル列）をハイライト。ボタン「詰まりを解消」＝ブロック中ロットを手運びでストッカーへ（ストッカー満杯なら先頭のロットを廃棄、確認あり） |
| ストッカー満杯 | 容量到達 | バナー。投入が止まる |

予防策：ストッカーが到達可能なら、装置の `.done` ロットは行き先装置が満杯でも「いったんストッカーへ」を選べる（スコアに +待ち時間として計上）。これでデッドロックは「ストッカーに繋がっていない閉路」に限定される。

### 1.8 オフライン進行（最重要）

比較：

| 方式 | 精度 | 計算量 | 復帰時の画面 | 欠点 |
|---|---|---|---|---|
| A. 全時間を本シミュレーション | 完全 | 2h実効 = 72,000ステップ。1ステップ ≈ ロット200＋装置60＋統計 ≈ 300演算 → 約2×10^7 演算、Release で 50〜150ms。上限が 12h・効率100% になると 432,000 ステップ ≈ 0.5〜1秒 | 自然（ラインが動いた状態） | 将来の上限拡大で起動が重くなる |
| B. 集計フォールバックのみ | 定常なら±数%。立ち上げ直後や詰まりがあると大きく外れる | ほぼ 0 | ロット位置が保存時のまま（止まって見える） | 「詰まっていたのに稼いだ」矛盾が起きる |
| C. ハイブリッド | シミュレート区間は完全、外挿区間は定常前提 | 予算で上限（12万ステップ ≈ 0.3秒以内） | 自然 | 実装が2系統 |

**推奨：C**。

- 手順：(1) 上限・効率は現行どおり（`offlineCapSeconds`, `offlineEfficiency`）。(2) 実効時間を `min(予算 120,000 ステップ, 実効ゲーム分)` だけ本シミュレーションで前進（価格は `recentAvgPriceYen` で固定、異常は発生しない、研究・補助金は実時間精算のまま）。(3) 残りがあれば、シミュレート区間の後半 50%（最低 6 ゲーム時間）の実測スループット・平均良品率・平均検出率から外挿し、資金・統計・学習枚数 W にのみ加算する。ロット位置・装置状態はシミュレート終了時のものを採用（定常ならそれが正しい末状態）。(4) ゲーム内時計・市況位相・プレイ秒は従来どおり戻す。
- 外挿の安全弁：シミュレート区間でデッドロック／寸断を検知していたら外挿スループットは 0（詰まったまま稼がない）。
- 精度目標（HeadlessCheck）：定常ラインで「オンライン 2 時間相当の tick 再生」と「オフライン C」の純収入差 ±3% 以内、シミュレート区間の完成ロット数は完全一致。
- 決定性：SimCore は乱数を使わないので、同じセーブ・同じ経過秒なら結果は再現する。

### 2.3 回転と向き（方針決定）

- **論理**：4方向（0/90/180/270）＋左右反転。フットプリントは 90/270 で幅と奥行が入れ替わる。ポートは外周セルのどこにでもレールを接続できる（向きは「正面」の位置とスプライトに影響するだけ）。
- **絵**：モデルごとに **正面向き・側面向きの 2 レンダリング**のみ制作。180/270 は左右反転で代用（ライティングは真上やや手前からに統一し、反転しても破綻しないようにする。§5.1）。
- 理由：4 方向 × 20 機種 × 5 レイヤーのセミフォトリアルを AI 生成で一貫させるコストは 2 方向の約 2 倍で、効果は「背面が見える」だけ。背面はゲーム上の情報を持たない。

### 2.4 配置バリデーション

- 配置可：購入済み区画内、他の装置・固定設備・レールと重ならない。レールの上には置けない（先に消す）。
- 移動：ドラッグで移動。ポートにロットがある装置は移動可（ロットは手運びでストッカーへ。ストッカーが無い／満杯なら移動不可）。処理中のロットの残り時間は保持。
- 売却：現行どおり価格の 50%。ポートのロットはストッカーへ。
- 倉庫（`storedEquipment`）：未配置の所有装置。配置は無料、外すのも無料（現行の detach/attach を踏襲）。
- 接続チェック（§1.7）：装置の「接続済み／未接続（入口・出口）」、ルートペアのチェックリスト、投入口→最初の工程、PKG→出荷口。
- 未接続装置の扱い：容量解析から除外、ロットの行き先候補にも入らない、絵はグレー。売却・改良は可能。ノード非対応の装置は現行どおり「待機」（グレー＋ラベル）。
- 「ストッカー経由なら全部つながる」を最初のチュートリアルで教える。チェックリストが全て ✓ になるとフロア上部に「ライン成立」のバッジ。

### 2.5 拡張区画

- 価格：現行の増床式を流用 `30億円 × 1.6^n`（n = 購入済み追加区画数）。補助金の累計投資には含めない（現行どおり）。
- 位置：既存区画に辺で接する 8×8 をタップで選ぶ。最大 6×6 区画。
- 旧セーブの `expansionCount` は追加区画数として無償付与（右→下の順で自動配置）。
- 1 区画 ≈ 小型装置 6〜8 台＋レール。現行の「+4 スロット」より広いが、レールが床を食うので体感はほぼ同等。

## 3. レール UX（スマホ）

### 3.1 モードと操作

| 操作 | 閲覧モード | 編集モード（レール） |
|---|---|---|
| 1本指ドラッグ | パン | レール描画 |
| 2本指 | ピンチズーム／パン | 同左 |
| タップ装置 | 詳細パネル | 選択（移動・回転・反転・売却ハンドル） |
| タップレール | 滞留情報 | 区間メニュー（向き反転／この区間を削除／分岐を追加） |
| 長押し | — | 消しゴムモード（ドラッグで削除） |

- 描画：指の軌跡をセルにスナップ。軸は「主軸を保ち、副軸に 1 セル以上ずれたら曲がる」ルールで Manhattan 化し、斜め移動の階段を防ぐ。角は自動でコーナー形状。
- 向き：ドラッグ方向＝流れの向き。ゴースト表示に矢印（シェブロン）を出す。
- コスト：1 セル 200 万円、ゴーストに合計を表示。資金不足分は赤くなり確定できない。削除は全額返金（レールは経済の対象ではなく配置の道具）。
- 既存レールから描き始める → そのセルが**分岐**（ルーターセル）になる。既存レールの上で描き終える → **合流**。1 セルに分岐は 1 つ（3 方向まで）。
- 直交する交差は**交差セル**として許可（2 レーン独立、立体交差の絵）。
- 装置の外周セルへ向けて終える → 入力ポート。装置の外周セルから描き始める → 出力ポート。
- アンドゥ 1 段（直前の描画・削除）。
- 編集中もシミュレーションは止めない。レールを消したセルにいたロットは手運びでストッカーへ（ストッカーが無ければ削除不可で理由を表示）。

### 3.2 搬送の視覚表現

- レール：床に埋め込んだ暗色トラック、方向シェブロンが速度に合わせて流れる（停止中は止まる）。
- FOUP：0.6 セルのベージュ箱（取っ手・窓・小さな影）。レール上は補間移動、装置のロードポートでは最大 4 個を整列、ストッカーでは数字バッジ（「×23」）。
- 滞留：停止中 FOUP に砂時計、連続 3 個以上の停止列でレールが黄色く脈動。
- ボトルネック：現行の赤枠脈動を装置単位に。

### 5.3 制作フロー（AI 生成＋仕上げ）

1. **スタイルアンカー**：承認済み CMP のカメラ・光・質感・パレットをリファレンスシートに固定（プロンプト定型＋画像参照）。
2. **本体生成**：モデルごとに正面・側面を img2img／参照付きで生成。1 機種あたり 8〜16 候補から選定。
3. **後処理**：アップスケール、背景除去、フットプリントに合わせた透視の微修正。
4. **レイヤー分離（手作業）**：可動部を切り出し、本体側の欠損をインペイント。可動部は別キャンバスで個別に整形（回転物は中心ピボットを明示）。
5. **ランプ**：全機種共通のシグナルタワー部品を手描きで 1 セット作り、配置座標だけ JSON に持つ。
6. **エフェクト**：Canvas の手続き描画（加算合成）。ラスタ資産を持たない。
7. **QA**：アプリ内デバッグ画面「スプライトビューア」で 4 方向・各状態・ポート位置を確認。
8. **順序**：初期 7 機種（L1, D1, E1, I1, C1, Q1, P1）→ 14nm 機（L2, D2, E2, Q2, P2）→ 残り 8 機種。

## 6. 描画／性能

### 6.1 データフロー

```
SimCore（Models、値型）
  → 4Hz で RenderSnapshot（ロット：セル＋progress／装置：状態・残り時間／レール占有／バッジ）
```

### C.5 P2 搬送再評価（2026-11-08）

P2（レール搬送）は完了。HeadlessCheck は 377 件すべて通過（HEADLESS CHECK PASSED）。以下は現行コード（`SimCore.stepRailTransport`）が実装している最終方式と、その実測値。

**搬送モデル**

- レール＋ブロッキング：1 セル 1 ロット（交差セルのみ直交方向の第 2 枠）、1 セル 3 ゲーム分。次セルが塞がっていればその場で待つ。`.rail` の `cellIndex` は `lot.path` のインデックス。
- ストッカーは容量 40、取り扱い時間 10 分。空きは「在庫 ＋ レール上でストッカーへ向かうロット」で数える（予約扱い。満杯のストッカーの入口でロットが待ち、払い出しの先頭セルを塞ぐ詰まりを防ぐ）。
- スコア ＝ 搬送時間（BFS 経路セル数 × 3 分）＋ 予想待ち。予想待ちは行き先の装置のポート状態と inbound（レール上で行き先がその装置のロット数）から求め、inbound は各フェーズ開始時にレール上のロットから数え直し、行き先を割り当てるたびに加算する。予想待ちのみで順位付けする形も試したが定常スループットは同等（7.90 WPH）だったため、近い装置が選ばれてレイアウトの巧拙が効く合計を採る。

**最終方式**

- 出発（処理済みロット）：無条件。行き先の空きは待たず、経路のある次工程の装置のうちスコア最小へ向かう。ストッカー経由は完全な迂回コスト「往路 ＋ 取り扱い 10 分 ＋ 復路（ストッカー → 最良の直接候補）＋ 最良候補の予想待ち」で評価し、直接の最良スコアより安い場合だけ選ぶ（混雑時の圧力逃がし、§1.7 の予防策）。経路のある候補が無ければストッカーへ退避する。出荷口行きは無条件。出発の物理的な条件は経路の先頭セルが空いていることだけで、塞がっていれば（または行き先が一つも無ければ）`.done` のままポートに留まる。
- 到着時の収容（行き先の装置の最終セルで）：(1) `.empty` ポートがあれば入線する（最小インデックス）。(2) 無く、行き先に `.done` ポートがある場合だけドライブスルーする。待つとその処理済みロットの出口を塞ぐため、現在セルがストッカーのポートなら直接収容 → ストッカーへ経路を付け替え → 同じ行き先へ循環経路でループ → どれもできなければ待つ、の順。(3) それ以外（全ポートが処理中・待機中）はその場で待つ。満杯のストッカーに着いたロットは循環経路があればループし、無ければ待つ。
- 払い出し（ストッカーから、取り扱い時間の経過後）：距離考慮型の計量。候補装置 T について、レール上で T へ向かうロットのうち残り経路セル数（`path.count − cellIndex`）がこの払い出し自身の経路セル数より小さいもの（自分より先に着くロット）だけを数え、その数 ＜ T の空きポート数 のときに候補とする。候補のうちスコア最小へ、経路の先頭セルへ出発できるときに払い出す。同じフェーズ内で払い出したロットも経路セル数で加える（スコアの予想待ちは全 inbound のまま）。ストッカー隣接の成膜への補充は即座に通り、長距離の払い出しにだけ流量調整が効く。
- 投入：無計量。条件は WIP ＜ WIP 上限、経路のある先頭工程の候補があること（スコア最小を選ぶ）、経路の先頭セルが空いていること、の 3 つのみ。戻りロットとのポート競合は到着時の収容で処理する。

**不採用とした方式（実測による）**

1. 出発ゲート（行き先に空きが無ければ元のポートで待つ／出発を空き見込みで制御）：ポートを空けるべき処理済みロットが出発できず、循環待ちになった（ポート数の少ない再入工程ラインで全装置のポートが処理済みロットで詰まった）。
2. 予約ゲート／特定ポート予約：ポート 1 つにロット 1 つの排他予約では補充のパイプラインが作れず、補充搬送の長いボトルネック装置（注入：処理 17.65 分に対し補充 78 分）が枯渇した。予約のロック・スワップ待ちの睨み合いなど、予約自体が競合資源になる凍結も繰り返し起きた。
3. 到着時刻とポート空き時刻のマッチング（just-in-time 振り分け）：処理済みポートを即空くとみなす見積もりが幽霊の容量を作り、処理済みロットの出発自体がその容量に依存する循環待ちになって凍結した。
4. 重力形のストッカースコア（ストッカー経由を「往路 ＋ 取り扱い ＋ 最良候補の待ち」で評価し、復路を数えない）：ストッカーに近い装置からストッカーが常に安く見え、迂回と往復が多発してストッカー滞留が平均 WIP の 58%（44.9 ロット中 26.3）を占めた。P1 では搬送が一律 24 分のためこの過小評価は表に出ていなかった。
5. 一律の inbound 計量（払い出し・投入とも inbound ＜ 空きポート数）：遠方を走行中のロットまで予約として数えるため、最頻工程の成膜では 600 分中 0 回しか計量を通らず、成膜行きがストッカーに滞留してライン全体が飢えた（投入を計量した場合も 600 分中 509 分が塞がれた）。
6. 無計量の払い出し：同じ装置への長距離の払い出しが行き先の前の行列になって環を溢れさせ、凍結した。
7. 到着時のストッカー迂回優先（全ポートが処理中・待機中ならストッカーへ迂回）：迂回交通そのものが環を塞ぎ、WIP 60 で完了 0 の完全凍結になった。
8. 到着時リルート（行き先が満杯なら空きポートのある兄弟装置へ付け替え）：無制限ではピンポンで凍結し、1 ホップ 1 回に制限しても定常運転が凍結した。

### C.6 P3 実装記録（2026-11-08）

> 実測値は 2026-11-09 の検証実行（HeadlessCheck 451 件全通過、HEADLESS CHECK PASSED）の print 出力から転記した。

**実装した方式**

- オフライン（`OfflineProgress.advance`、§1.8 方式 C）：上限・効率は `Engine.offlineCapSeconds` / `offlineEfficiency` のまま。実効ゲーム分のうち `min(予算 120,000, 実効ゲーム分)` を整数ステップだけ `SimCore` で本シミュレーションし（価格は `market.recentAvgPriceYen` で固定）、残りを計測窓のレートで外挿する。計測窓は後半 50%（最低 360 ゲーム分、区間全体が上限）。外挿は資金・Stats・学習枚数 W にだけ加え、`Fab.sim` はシミュレーション終了時の状態（外挿分のロットは入れない）。ゲーム内時計・市況・プレイ秒は進めず、異常も発生させない。
- 外挿の安全弁：`LayoutAnalysis` のライン寸断（layout がある場合のみ）、終了時の `isDeadlocked`、計測窓の完了スループット 0 のいずれかで `lineJammed` とし、外挿しない。
- セーブ v4：`Fab.placed / layout / sim / nodeSwitch`、`Stats.completedLots / scrappedLots / railCellsBuilt / parcelsBought`、`ActiveExcursion.causeToolId` を追加（すべて decodeIfPresent で旧セーブ互換）。`SimSnapshot` は lots を投入順で持ち、`SimCore(state:snapshot:)` で復元する（経路キャッシュ等はレイアウトから作り直すので結果は変わらない）。
- v3 → v4 移行（`Engine.migrateToLayout`）：テンプレート → 増床回数ぶんの区画を読み順で無償付与 → 区画が増えた場合だけ倉庫行きを y → x 走査で貪欲配置 → 残りは倉庫。id・Lv・購入日を保持し、`fab.equipment` は配置済み装置と同じ集合にする。発生中の異常は解除（クールダウン据え置き）、`wipWafers` は読まない。
- SimCore の数値挙動は変えていない。追加は観測専用（`SimStats.sumGrossYen / sumCogsYen / sumPenaltyYen`、`throughputEMA / yieldEMA / detectionEMA / incomeEMA / cycleTimeEMA / pendingMinutes`）と入出力 API（`snapshot()` / `init(state:snapshot:)` / `freshSnapshot`）だけ。

**指示からの細部の判断・逸脱**

1. 計測窓の開始はステップ境界へ切り上げ、実際に s1 を取ったステップから窓長を数える（シミュレーション区間が奇数分のときに窓長と実測区間がずれないようにするため）。
2. 窓長が 0（シミュレーション 0 ステップ）のときはスループット 0 判定をしない（測っていないため）。外挿もしない。
3. 外挿分は `Fab.sim.stats` には加えない（スナップショットは実在するシミュレーション状態だけを持つ）。
4. HeadlessCheck のフィクスチャから v4 キーを除く際、fab の 4 キーに加えて Stats の新キー 4 種も除いた（より本物の v3 形式に近づけるため。読み込みは decodeIfPresent で互換）。
5. 精度チェック A の比較対象（全量シミュレーション）も `settlementPriceYen` を `recentAvgPriceYen` に上書きしている（advance と同じ価格条件で完全一致を見るため）。

**P4 以降への申し送り（今回は挙動を変えずに残した）**

- `freshSnapshot` は SimCore の既定の `wipCap = 200` を持つ。C.5 のとおり 16×16 テンプレートは 52 ロット以上で凍結するため、新規ゲーム・移行直後のセーブをそのまま `advance` すると寸断なしでも詰まり判定になりうる。運転点（45）の設定場所を P4 で決める必要がある。
- SimCore の学習 W はシミュレーション内の `stats.releasedWafers`（投入時点の値）で、`GameState.learningWafers` とは連動していない。移行直後の sim は W = 0 から始まるため、学習の進んだセーブでは歩留まりが初期値に戻る。
- 手動販売（`autoSellEnabled == false`）のとき、`advance` は Stats の売上系（`totalRevenueYen` 等）を全量で加えつつ、チップは在庫に積む（指示どおり）。在庫を後で売ると売上系が二重計上になりうる。
