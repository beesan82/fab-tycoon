## 1. 生成（試行回数・没率）

生成はコストと一貫性のため「2機種を横並び・無地明背景・**シグナルタワーなし**」で3枚＋単体1枚。スタイル参照には承認済みCMPサンプル画像を渡した。

| 生成 | 対象 | 結果 |
|---|---|---|
| 1回目 | L1＋I1（ペア） | L1は採用。I1は斜め構図でペア分割できず**不採用**（下記 §2） |
| 1回目 | D1＋E1（ペア） | 両方採用 |
| 1回目 | Q1＋P1（ペア） | 両方採用（Q1は後処理で穴埋めが必要だった） |
| 2回目 | I1（単体） | 採用。水平ビームライン構図で一発成功 |

- 生成画像単位の没率は 4回中0回（全て何らかの形で採用）。機種単位では I1 のみ作り直し（ペア版を破棄し単体版を採用）
- **タワーは全機種で描かれなかった**（プロンプト統制が効いた）。状態ランプは従来のコード描画が正、という前提が量産でも成立した
- 実在メーカー機の酷似回避：全機種とも一般化した姿で、ロゴ・モデル名・文字は無い（P1前面の小さなパネル図柄のみ。文字ではない）

## 2. 後処理（make_sprites.py、試行3世代）

第1ゲートの `make_c1_sprites.py` を一般化した `design/sprites/make_sprites.py` を新設。背景除去（フラッドフィル）は再利用し、分割と掃除は3世代の試行錯誤があった。

| 世代 | 方式 | 結果 |
|---|---|---|
| 1 | 連結成分の重心への最近傍割当で2分割 | **失敗**。斜めの切断線が両機種を切り裂いた（D1にE1の断片が混入等） |
| 2 | 中央付近で最も空いている縦列で分割＋影の許容差を「暗い側だけ」非対称に拡大（影のコアが本体に付いて残る問題への対処） | 分割は成立。ただし L1 に I1 のタンク断片が残留、Q1 の白パネルに抜け穴 |
| 3 | 断片掃除を bbox 基準→**本体マスク膨張との近接基準**に変更＋**内部の抜け穴埋め**（端に接しない透明領域を本体として復元）を追加 | **全6機種でクリーンに分離**（コンタクトシートで目視確認済み） |

- I1 のペア版が救えなかった理由：ビームラインが右上→左下の対角線構図で、どの縦列でもう一方の機種と x 範囲が重なった。単体生成（水平構図）に切り替えて解決
- Q1 の抜け穴の理由：白いパネル面が背景色に近く、フラッドフィルが継ぎ目から内部へ漏れた。穴埋めで復元できたが、前面下部にわずかな色むらが残る（knownIssues に記録）

## 3. 容量実測（本体、@3x相当）

| 機種 | footprint | ピクセル | 容量 |
|---|---|---|---|
| L1 露光 | 4×3 | 652×578 | 368 KiB |
| D1 成膜 | 2×2 | 576×593 | 377 KiB |
| E1 エッチ | 2×2 | 576×763 | 347 KiB |
| I1 注入/熱 | 4×2 | 1152×326 | 392 KiB |
| C1 CMP（第1ゲート） | 2×2 | 576×549 | 本体 373 KiB＋可動部 154 KiB |
| Q1 検査 | 2×2 | 576×1028 | 391 KiB |
| P1 PKG | 2×2 | 576×642 | 309 KiB |
| **初期7機種 合計** | | | **2.65 MiB** |

- 全機種とも仕様帯（本体 80〜400KB/点、redesign §5.4）に収まった
- §5.4 の総見積もり（全20機種×2方向＋可動部＋環境 ≒ 12.5MB）との比較：front のみ7機種で 2.65MB。同じ単価で 20機種×2方向を外挿すると約 15MB となり、**見積もりをやや超える見込み**。本VMには pngquant が無く未適用のため、本番取り込み時に pngquant／アセットカタログ圧縮で削る余地がある

## 4. メタデータと配置

- `design/sprites/<id>.json`（正本、C1と同形式：footprint・loadPorts は Simulation.swift の `simFootprint`／`simLoadPortCount` と照合済み）＋ `Assets.xcassets/eq_<id>_meta.dataset` へ同梱
- 本体画像は `eq_<id>_front_body.imageset`。**pbxproj は無変更**（第1ゲートの方式を踏襲）
- **コード変更はゼロで6機種が描画対象になった**（第1ゲートで作ったフォールバック機構の狙いどおり）。`layers` は空配列（可動部なし）。drawScale は全て初期推定値：L1 1.15／D1 1.25／E1 1.20／I1 1.05／Q1 1.00／P1 1.25（C1 は 1.28 のまま）
- 機種固有の注意は各 JSON の knownIssues に記録。主なもの：L1 は対角線構図で斜め置きに見える可能性、Q1 は顕微鏡コラムが高く縦オーバードロー大（drawScale 1.00 でも約3.6セル高）、I1 は他よりやや正面寄りの視点

## 5. 環境一式（基礎分）

「β2で効く順」に優先順位をつけ、以下3点を **Canvas 手続き描画の上乗せ**（アセット 0KB追加）で実施した。変更は `FabTycoon/Views/FloorGridView.swift` のみ。

| 優先 | 要素 | 内容 |
|---|---|---|
| 1 | 床タイル | 購入区画のセルに市松の濃淡（パネル感）＋セル下端にグレーチング孔ドットを追加 |
| 2 | ストッカー | べた塗り＋「ST」文字 → ラック枠＋棚グリッド＋収納数ぶんのミニ FOUP スロット表示に変更（0個のときだけ ST 表示） |
| 3 | FOUP | ベージュ矩形 → 接地影・蓋の継ぎ目・前面の窓帯・取っ手を追加 |

申し送り（β2範囲外としたもの）：
- 装置背後の配管・ダクト・ケーブルトレイの背面レイヤー（ラスタ資産が必要で、機種側の絵が実機で確定してから合わせる方が手戻りが少ない）
- 床の安全ライン（黄色線）・エリア区画線（描画自体は軽いが、レール・装置との重なり順の設計が要る）
- 投入口（IN）／出荷口（OUT）の作り込み（現状は色矩形＋文字のまま）
- 床のラスタタイル化（手続き描画で足りるか実機で見てから判断）
